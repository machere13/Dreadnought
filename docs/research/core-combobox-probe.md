# Проверка core на кастомном Combobox

Дата: 2026-10-05.

## Что проверяли

Можно ли собрать поисковое поле со списком, одиночным выбором и клавиатурой из публичного `@dreadnought/core`, без готового Select, React-адаптеров библиотеки и слоя оформления.

Проба находится в `packages/core/tests/probes/combobox/ComboboxProbe.tsx`. Это **тестовый эксперимент, не публичный компонент**, не обещание полного API Combobox и не образец законченного дизайна. В сборку пакета он не входит. React используется только как владелец состояния и связка с обычными HTML-элементами; production-core не зависит от React.

## Что получилось переиспользовать

| Задача | Уже существующий публичный core |
|---|---|
| Поиск по label без учёта регистра, выбранные пункты | `getSelectState` |
| Перевод ArrowUp/ArrowDown в направление без перехвата Home/End | `getNavigationDirection` |
| Доступный активный пункт, пропуск disabled, остановка на краях | `getNextEnabledValue` |
| Одиночный выбор с ограничениями | `getSelectionValue` |
| Запрос открытия/закрытия | `getDisclosureOpen` |

Никакие функции не скопированы из `useSelect`, новые behaviors/actions не добавлены. Строковые label/value соответствуют существующему контракту Select core. Обработка произвольных объектов и сложных подписей не проверялась.

## Что осталось в пользовательской связке

- React-состояние: выбранное значение, поисковый черновик, активный пункт, открытие.
- Решение, когда открыть список, сбросить черновик и подтвердить выбор.
- DOM/ARIA: уникальные ID, `combobox`, `listbox`, `option`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, `aria-selected`.
- События: `preventDefault`, отмена обработчиком пользователя, IME, закрытие по Escape/Tab/уходу фокуса.
- Фокус остаётся в поле; выбор мышью не должен уводить его на пункт.

Это код адаптации к интерфейсу и DOM, а не отсутствующий чистый алгоритм. `getDisclosureState` сюда не подставлялся: его button/панель с `aria-labelledby` — контракт секции Disclosure, а не доступность Combobox. Совпадение флага open не делает эти паттерны одинаковыми.

## Доказательства и границы

Сценарные тесты `ComboboxProbe.test.tsx` проверяют поиск, подтверждение без submit, навигацию без disabled и wrap-around, сохранение курсорных клавиш, Escape без изменения значения, Tab без перехвата фокуса, пустой результат, выбор мышью, IME, отменённые события, disabled-поле, разные ARIA-цели двух экземпляров и отсутствие коллизий ID с ключами вариантов `input`/`list`.

Запуск из корня: `node node_modules/vitest/vitest.mjs run packages/core/tests/probes/combobox/ComboboxProbe.test.tsx`.

Это проверки событий и DOM в jsdom, **не проверка скринридером или реальным браузером**. Список обычный inline: native popover, portal, позиционирование и вложенные окна в этой пробе не исследуются. Также не реализованы controlled API, multiple, асинхронный поиск, виртуализация, сериализация формы, валидация и reset. Поиск здесь — поиск среди вариантов, а не разрешение вводить произвольное значение.

## Вывод

Для проверенного сценария существующего core достаточно. Добавлять `getComboboxState`, универсальный controller или popup-stack ради пробы не нужно.

Заметная связь: поиск сейчас находится в компонентном `getSelectState`, а не в самостоятельном behavior. Это допустимое переиспользование первого слоя. Выделение общего поиска стоит рассматривать при реальном потребителе с другим контрактом данных, а не только ради перемещения функции в папку behaviors.

Эта проба не доказывает обещание «можно собрать любой компонент». Следующая полезная проверка — другой класс взаимодействия, например изменение числового значения с шагом и границами; он проверит возможность, которой этот Combobox вообще не касается.
