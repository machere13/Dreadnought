# Проверка core на кастомном NumberField

Дата: 2026-10-05.

## Что проверяли

Можно ли собрать числовое поле с собственными кнопками увеличения/уменьшения без готового Input, адаптеров и оформления библиотеки.

Проба: `packages/core/tests/probes/number-field/NumberFieldProbe.tsx`. Она находится только в тестах, не является публичным компонентом и не входит в сборку core. React связывает состояние с обычными HTML-элементами; production-core не зависит от React.

## Разделение ответственности

| Задача | Кто выполняет |
|---|---|
| Флаги disabled/readOnly/required/invalid | Публичный `getTextFieldState` |
| Направление вертикальной стрелки без перехвата Home/End | Публичный `getNavigationDirection` |
| Числовой ввод, шаг, привязка к step base, границы и дробные значения | Нативный `input type="number"`, `stepUp()`/`stepDown()` |
| Проверка диапазона, шага и обязательного значения | Нативная `ValidityState` |
| Значение формы и сброс к defaultValue | Нативная форма |
| События, синхронизация отображаемого значения/aria-invalid, фокус | Тестовая React-связка |

У навигации `previous` означает ArrowUp, а `next` — ArrowDown. В числовом поле ArrowUp увеличивает, ArrowDown уменьшает: адаптер связывает эти направления с соответствующим нативным методом. IME, отменённые события и модификаторы не перехватываются.

Ввод не исправляется автоматически: значение вне диапазона или шага остаётся в поле и помечается invalid. Пустая строка не превращается в ноль. Кнопки используют `type="button"`, не отправляют форму и возвращают фокус полю. И disabled, и readOnly блокируют шаг; проверка `:disabled` также учитывает fieldset. Сброс формы синхронизирует отображение после нативного reset и не выполняется при отмене события.

## Проверки и границы

Десять сценарных тестов проверяют синхронизацию поля, отображения и FormData; отсутствие submit; фокус; границы, не кратные шагу; дроби; invalid-ввод; обязательное пустое поле; клавиатуру/IME/отмену события; disabled/readOnly/disabled fieldset; обычный и отменённый reset.

Запуск из корня:

```sh
node node_modules/vitest/vitest.mjs run packages/core/tests/probes/number-field/NumberFieldProbe.test.tsx
```

Проверки выполнены в jsdom, не в реальном браузере или скринридере. Это ограниченный uncontrolled-сценарий с конечными числовыми значениями и положительным конечным числовым step. `step="any"`, форматирование/локализованные разделители, денежная точность, большие числа, controlled API, динамическая смена формы, удержание кнопки и колесо мыши не исследуются. Различия браузеров при промежуточном вводе вроде `-`/`1e` также не проверены. При изменении через stepUp/stepDown проба сама синхронизирует своё отображение; отдельного публичного onValueChange API у неё нет.

## Вывод

Для этого нативного сценария новая арифметика в core не понадобилась: браузер уже предоставляет шаг, ограничения и валидацию. Проба использует core для флагов поля и определения направления, но **не доказывает, что core уже умеет чистое изменение числового значения без DOM**.

Чистый behavior шага остаётся кандидатом для потребителя, которому нативного input недостаточно, например кастомного Slider. Не добавляем его только ради копирования stepUp/stepDown. Не переносим DOM-методы или React-состояние в core и не утверждаем по этой пробе, что можно собрать любой компонент.
