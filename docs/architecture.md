# Архитектура библиотеки компонентов

Статус: архитектура принята за основу реализации; первый компонент — Button.

Документ определяет устройство продукта и границы ответственности. Здесь нет календарного плана. Публичные примеры используют текущий npm-scope `@dreadnought`. Правила размещения тестов и именования: [conventions.md](conventions.md).

## 1. Назначение

Библиотека предоставляет переиспользуемые UI-компоненты на трёх уровнях: логика и API, структура и адаптация под фреймворк, дизайн-система. Разработчик и AI-агент могут использовать любой уровень напрямую и комбинировать их через публичные контракты.

Ключевой принцип: `core` служит конструктором не только для компонентов, поставляемых библиотекой. Цель — чтобы большинство задуманных пользователем веб-компонентов, включая нестандартные и сложные, можно было собрать полностью из возможностей `core` либо переиспользовать из него большую часть логики, действий и правил взаимодействия. Поэтому `core` развивается как набор комбинируемых возможностей, а не только как внутренности готовых компонентов. Это целевое свойство, которое предстоит проверить на разных классах компонентов; текущая реализация Button сама по себе его ещё не доказывает.

Сама библиотека работает без LLM, MCP и Figma. AI-инфраструктура помогает применять её в проекте. Figma служит дополнительным источником дизайн-системы; пользователь также может описать её вручную.

Первый поддерживаемый фреймворк — React. Архитектура допускает другие адаптеры, но не требует заранее реализовывать их.

Первая версия рассчитана на веб. `core` не зависит от React, Vue, Svelte, Angular или способа генерации HTML; браузерный код может использовать его и в проекте на Rails. React Native и другие невеб-платформы не входят в текущую область проекта. Доступность функций `core` в разных веб-проектах не означает, что готовые React-компоненты работают в них без отдельной реализации.

## 2. Три слоя

| Слой | Ответственность | Публичный результат | Чего в нём нет |
|---|---|---|---|
| 1. Логика и API | Состояния, действия, правила взаимодействия, семантика, доступность | Независимые функции и контракты; хуки соответствующего фреймворка | Готовой разметки и оформления |
| 2. Структура и адаптация под фреймворк | Разметка, порядок частей, слоты, refs и связь логики с элементами интерфейса | Компоненты без визуальной темы | Цветов, типографики, декоративных размеров и анимаций |
| 3. Дизайн-система | Общие токены и CSS, применение оформления к адаптерам разных фреймворков | Готовые компоненты через точки входа `ui/react`, в будущем `ui/angular` | Повторной реализации поведения и семантики |

Целевая зависимость: визуальный слой использует адаптер своего фреймворка, адаптер использует `core`; обратных зависимостей нет. Слой 2 адаптирует логику к фреймворку, слой 3 адаптирует общую дизайн-систему к результату слоя 2. Это разные виды адаптации. Подробное решение: [два вида адаптации](superpowers/specs/2026-09-26-layered-adapters-design.md).

Каждый уровень доступен напрямую. Пользователь может взять готовую кнопку, оформить базовую кнопку самостоятельно или построить собственную разметку на логике первого слоя.

Слой 3 включает общие тему и CSS Modules плюс тонкие фасады под поддерживаемые фреймворки. Целевой `@dreadnought/ui/react` экспортирует готовый `Button`, построенный поверх `ButtonAdapter`, и сам подключает стандартное оформление. Для Angular потребуется и адаптер второго слоя, и тонкий фасад третьего; общие стили и токены не дублируются. Текущий код ещё не перенесён на эту схему.

### Граница логики и фреймворка

React-хук не может быть независимым от React. Поэтому первый слой состоит из двух частей:

- Общее ядро: правила, контракты и действия без зависимости от UI-фреймворка и готовой разметки. Браузерные API допускаются внутри веб-действий, но не вызываются при импорте модуля.
- Адаптация поведения: React-хуки, события, фокус, refs и привязка семантики к DOM.

Обе части относятся к первому слою по ответственности, но находятся в разных пакетах. Будущий Vue-адаптер сможет использовать общее ядро и реализовать свои composables. Выделять в ядро нужно только действительно общую логику, а не абстрагировать каждый вызов React.

Для простой кнопки достаточно нативного `<button>` и небольшой адаптации состояния. Универсальный движок состояний для всех компонентов заранее не нужен.

### Состав `core`

| Часть | Ответственность | Пример |
|---|---|---|
| `behaviors/` | Переиспользуемые правила изменения состояния и выбора следующего действия, без разметки и внешних эффектов | Переход к следующему доступному пункту |
| `patterns/` | Целостные веб-контракты доступности: семантика, клавиатура и фокус вместе с необходимыми правилами поведения | Раскрываемая область (`Disclosure`) |
| `actions/` | Действия, не принадлежащие конкретному компоненту; могут использовать браузерные API | `copy(text)`, `download(blob, filename)` |
| `domains/` | Специализированные алгоритмы и модели, нужные семейству сложных компонентов | Модель Markdown-документа, шкалы и геометрия графиков |
| `components/` | Контракт и композиция логики конкретного известного компонента | Состояния Button, контракты MarkdownEditor и RadarChart |

Это категории ответственности, а не обязательные папки для каждого компонента. Семантику нельзя составлять из разрозненных ARIA-атрибутов без правил клавиатуры и фокуса. Специфичное остаётся в `components/` или `domains/`; в общие `behaviors/` и `patterns/` выносится только проверенно переиспользуемое. Типы хранятся рядом с соответствующей логикой.

Для нового компонента разработчик или агент выбирает подходящие действия, поведения, доступные паттерны и доменные алгоритмы `core`, дополняет недостающее и создаёт разметку в своём фреймворке. `core` может покрыть всю или большую часть логики, но не заменяет слой реализации и дизайн-систему.

Проверка границ на трёх случаях: Button использует собственный контракт и нативную семантику `<button>` — ему не нужны все категории `core`. MarkdownEditor требует модели документа в `domains/`, контракта в `components/` и, по ситуации, общих действий и доступного паттерна панели инструментов. RadarChart требует шкал и геометрии в `domains/`, контракта в `components/`; выбор серий и клавиатурный доступ добавляются, если график интерактивен. Наличие категории не обязывает каждый компонент использовать её.

## 3. Структура репозитория

Ниже показано текущее размещение файлов до миграции фасадов в третий слой; целевое размещение описано в спецификации выше.

```text
packages/
  core/                         # Независимая часть слоя 1
    src/
      actions/                   # Появляется с первым общим действием
      behaviors/                 # Появляется с первым общим правилом
      patterns/                  # Появляется с первым общим паттерном доступности
      domains/                   # Появляется с первой специализированной моделью
      components/
        Button/
          ButtonCore.ts
          getButtonState.ts
      index.ts
    tests/
      components/
        Button/
          getButtonState.test.ts

  adapters/                    # Слой 2: структура и адаптация под фреймворки
    react/
      src/
        Button/
          useButton.ts          # React-хук для поведения слоя 1
          ButtonAdapter.tsx     # Выбор кнопки или ссылки по href
          ButtonActionAdapter.tsx # Нативный button и привязка useButton
          ButtonLinkAdapter.tsx # Нативная ссылка и блокировка перехода
          renderButtonContent.tsx # Общий порядок иконки и текста
          Button.tsx         # Оформленный React-фасад поверх ButtonAdapter
        logic.ts                # Экспорт хуков
        unstyled.ts             # Экспорт базовых компонентов
        styled.ts              # Экспорт готовых React-компонентов и CSS
      tests/
        Button/
          useButton.test.tsx
          ButtonAdapter.test.tsx

  ui/                           # Независимое от фреймворка оформление слоя 3
    src/
      Button/
        buttonPresentation.ts
        Button.module.css
    tests/
      presentation.test.ts

  themes/                       # Значения темы и типографика слоя 3
    src/
      default/
        tokens/
          global/
            colors.tokens.css
            spacing.tokens.css
            sizing.tokens.css
            typography.tokens.css
            effects.tokens.css
            motion.tokens.css
          components/
            Button/
              colors.tokens.css
              spacing.tokens.css
              sizing.tokens.css
              typography.tokens.css
              effects.tokens.css
              motion.tokens.css
        components/
          Button/
            typography.css
        index.css

examples/
  react/                        # Потребитель публичного API библиотеки

docs/
  architecture.md
  conventions.md
  components/
    button.md

tools/                          # Появляется при реализации генератора каталога
  catalog/

graphify-out/                   # Генерируемая карта исходного кода
```

Это схема размещения для реализованных частей. Пустые папки, утилиты, дополнительные адаптеры и файлы «на будущее» не создаются. Для первого компонента добавляются только необходимые части.

Код группируется по компоненту. Рядом видны его поведение, разметка, оформленный вариант, описание и проверки. Общая утилита выделяется, когда несколько компонентов действительно используют одинаковый контракт.

Пример приложения нужен для проверки библиотеки как внешним потребителем. Он не содержит скрытых исправлений, без которых компоненты не работают.

## 4. Пакеты и зависимости

Таблица и пример ниже фиксируют текущий API до миграции. Целевой публичный импорт готового React-компонента — `@dreadnought/ui/react`; адаптера без оформления — `@dreadnought/react/unstyled`. Готовая точка входа сама подключит стандартные стили и тему.

| Пакет | Зависимости | Назначение |
|---|---|---|
| `@dreadnought/core` | Без UI-фреймворков; веб-API допустимы внутри действий | Общие контракты, поведения, паттерны, действия и доменная логика |
| `@dreadnought/react` | `core`, `ui`; React как peer dependency | React-хуки, базовые и оформленные фасады компонентов |
| `@dreadnought/ui` | Без React и других UI-фреймворков | CSS Modules, собранный CSS и публичные карты классов |
| `@dreadnought/themes` | Без React и JavaScript runtime | Стандартные токены и шрифтовые классы |

Для репозитория используется workspace. Начальный вариант — pnpm и TypeScript. Инструменты разработки и генерации не попадают в зависимости пользовательского приложения.

Пакеты первоначально выпускаются согласованным набором версий. Это упрощает совместимость ядра, адаптера, темы и каталога. Независимое версионирование вводится только при реальной необходимости.

Предлагаемые публичные импорты:

```tsx
import { useButton } from '@dreadnought/react/logic';
import { ButtonAdapter } from '@dreadnought/react/unstyled';
import { Button } from '@dreadnought/react/styled';
import '@dreadnought/themes/default.css';
```

Импорт темы явный. `@dreadnought/react/styled` подключает CSS из `ui`, но не стандартную тему. Подключение хуков или базовых компонентов не должно автоматически приносить стили. Другой адаптер вправе использовать `@dreadnought/ui` и его `style.css`, не импортируя React.

Внутренние файлы не являются публичным API. Потребитель работает через объявленные точки экспорта. Сборка должна выпускать модули, декларации типов и CSS; исходники демо, тесты и инструменты в пакет не включаются.

## 5. Контракт компонента

У каждого компонента описываются:

1. Назначение и ограничения.
2. Входные свойства и события.
3. Поддерживаемые состояния и кто ими управляет.
4. Семантика и клавиатурное взаимодействие.
5. Части разметки и доступные слоты.
6. Визуальные варианты и токены.
7. Допустимые способы расширения.

Это контракт для разработчика, тестов и AI-каталога. Он не требует универсального базового класса или наследования всех компонентов от одного типа.

### Владение состоянием

- У каждого состояния один владелец.
- Управляемое состояние приходит из проекта; компонент сообщает о запросе изменения.
- Неуправляемое состояние принадлежит соответствующему хуку.
- Базовый и оформленный компоненты не создают вторую копию состояния хука.
- Дизайн-система читает состояния, но не меняет их.

Поддержка управляемого и неуправляемого режима добавляется только там, где у компонента действительно есть такое состояние.

### События и расширение

Компонент предоставляет стабильный публичный API, передачу стандартных DOM-свойств и ref на оговорённый элемент. Слоты добавляются для реальных частей компонента, а не как универсальная система произвольной перестройки DOM.

Обработчики нельзя объединять простым перезаписыванием через spread. Если компоненту нужны внутренний и пользовательский обработчики одного события, их порядок и влияние `preventDefault()` определяются в контракте и проверяются тестом.

Универсальный `mergeProps` не считается безопасным решением для любых комбинаций: `className`, события, refs и ARIA-связи имеют разные правила объединения. Общие помощники вводятся для конкретных повторяющихся случаев.

## 6. Как комбинируются слои

Четыре поддерживаемых сценария:

| Сценарий | Использование |
|---|---|
| Стандартный интерфейс | `Button` + стандартная тема |
| Собственная дизайн-система | `Button` + пользовательская тема; `ButtonAdapter`, если нужно полностью своё оформление |
| Нестандартная структура | `useButton` + собственная разметка в рамках семантического контракта |
| Нет готового компонента | Собственный компонент из доступных возможностей `core`, с собственной разметкой и темой |

Если готового компонента нет, разработчик или AI-агент собирает его из доступных частей первого слоя: поведений, доступных паттернов, действий и доменных алгоритмов. API, семантика и клавиатурное взаимодействие нового компонента определяются как единый контракт, а не складываются из случайных ARIA-атрибутов. Недостающая часть реализуется в проекте; в `core` она переносится, когда появляется повторное применение. Текущий `core` содержит правила Button и общие действия, поэтому сборка произвольного компонента без нового кода пока не гарантируется.

Добавление функции к готовому компоненту не означает повторное подключение его собственного поведения. Существующее действие `copy(text)` может использоваться напрямую или внутри будущего React-хука, который дополнительно управляет статусом операции:

```tsx
// Иллюстрация композиции; useClipboard пока не реализован.
const { copy, pending } = useClipboard();

<Button onClick={() => copy(text)} loading={pending}>
  Скопировать
</Button>
```

Хук управляет операцией копирования, кнопка — своим взаимодействием и отображением состояния. Два независимых обработчика не пытаются одновременно владеть поведением кнопки.

Если тема не может выразить нужную структуру, используется слой 2. Если структура слоя 2 не подходит, используется слой 1. Эти переходы доступны отдельно для каждого компонента в одном проекте.

## 7. Дизайн-система

Слой дизайна состоит из трёх частей:

- Глобальные токены: абстрактные нецветовые шкалы (`spacing-x1`, `border-radius-x1` и т. д.) и смысловые цвета (`color-action-primary`, `color-text-primary`, `color-focus-ring`). Их имена не зависят от конкретного компонента.
- Токены компонентов: назначают общие значения конкретным свойствам и состояниям (`button-padding-x`, `button-primary-bg`). Уникальное для компонента значение может задаваться напрямую, без искусственного глобального токена.
- CSS Modules компонентов: применяют токены к частям, состояниям и визуальным вариантам; карты классов экспортируются для адаптеров разных веб-фреймворков.

Готовый компонент оформляется только локальным CSS Module. Все его настраиваемые визуальные значения читаются из публичных CSS-переменных темы: пользователь меняет токены, а не переопределяет селекторы компонента. Если повторяющейся настройке не хватает токена, он добавляется в контракт библиотеки. Другая структура собирается из слоя 2 или 1 со своим CSS Module.

Пример стабильных точек оформления: `data-ui="button"`, `data-slot="label"`, `data-loading`, `data-variant`. Конкретный набор фиксируется для каждого компонента. Тема не должна зависеть от случайной глубины DOM или внутренних имён файлов.

Токены задаются CSS custom properties. Темы можно ограничивать контейнером, чтобы несколько дизайн-систем сосуществовали на странице. Отдельные глобальные классы `.dreadnought-text-*` задают шрифты и читают типографические токены; остальные селекторы компонентов находятся только в CSS Modules. Библиотека не добавляет глобальный reset приложения.

Анимации задаются в слое 3. Состояния и жизненный цикл, необходимые для анимации, предоставляет нижний слой. Скрытие элемента, управление фокусом и его удаление из DOM не переносятся в тему.

Замена темы сохраняет логику компонентов, но не гарантирует всю доступность автоматически: контраст, видимость фокуса, движение и размеры интерактивных областей требуют проверки новой темы.

## 8. AI-каталог и Graphify

AI-инфраструктура находится вне runtime библиотеки и описывает все три слоя.

```text
Публичные экспорты + TypeScript-типы + явные метаданные
                         ↓
                  Генератор каталога
                         ↓
            Версионированный каталог компонентов
                         ↓
                      Skill / MCP
                         ↓
                  Агент в проекте пользователя
```

Каталог содержит пути импорта, свойства, состояния, доступные уровни, части разметки, точки настройки темы, ограничения и проверенные примеры композиции.

Экспорты и типы извлекаются из кода. Семантические ограничения, например «этот хук рассчитан на нативный button», задаются явно рядом с компонентом. Их нельзя надёжно восстановить только по графу вызовов.

Каталог — производный результат сборки. Он имеет версию формата и версию библиотеки. Проверка сборки должна обнаруживать ссылки на несуществующие экспорты и устаревшие примеры.

Graphify используется для навигации по исходникам и анализа связей между ядром, хуками, компонентами и оформлением. Его граф может дополнять каталог, но не подменяет публичные контракты автоматически выведенными связями. Предположения и извлечённые из кода факты должны оставаться различимыми.

Skill объясняет агенту порядок выбора слоя и использования каталога. MCP предоставляет доступ к нужным записям, если такой транспорт требуется. Внедрение MCP не является условием работоспособности компонентов.

Агент получает сведения для установленной версии библиотеки и запрашивает только относящиеся к задаче компоненты. Это гипотеза сокращения контекста и повторной работы; экономия времени и LLM-токенов подтверждается измерениями.

## 9. Figma

```text
Figma → извлечение данных → сопоставление с контрактом темы
      → предлагаемые изменения темы → проверка в проекте
```

AI-агент помогает сопоставить названия, варианты и визуальные правила Figma с токенами темы библиотеки. Он предлагает изменение CSS-файлов темы проекта, а не исходников библиотеки или поведения компонентов.

Если дизайн требует другой структуры, агент сообщает об ограничении текущего компонента и использует доступные способы слоя 2 или 1. Нельзя молча объявлять такое изменение обычной сменой темы.

Результат интеграции — обычные файлы дизайн-системы в проекте, доступные для ручного изменения и контроля версий. Для повторной синхронизации сохраняются соответствия элементов Figma и элементов темы; локальные изменения показываются как конфликт, а не перезаписываются безусловно.

Внешние данные из Figma рассматриваются как данные дизайна, а не как инструкции агенту.

## 10. Первый компонент: Button

Таблица показывает целевую ответственность файлов; текущий оформленный фасад пока расположен в React-пакете.

Первый Button проверяет все три слоя и независимое использование каждого.

| Уровень | Содержимое |
|---|---|
| Общее ядро | Контракт состояний `disabled` и `loading`, общие правила доступности действия |
| React-логика | `useButton`: вычисление свойств нативной кнопки, защита действия в недоступном состоянии |
| Компонент второго слоя | `ButtonAdapter`: нативный `<button>` для действия или `<a>` при `href`, ref, содержимое, `icon`/`iconPosition` и стандартные DOM-свойства |
| Третий слой | `ui/react` экспортирует `Button`: применяет общий CSS Module к `ButtonAdapter` и подключает стандартную тему |
| Общий визуальный контракт | CSS и токены обычного состояния, hover, active, focus-visible, disabled и loading; переиспользуются для других веб-фреймворков |

Правила первого Button:

- По умолчанию `type="button"`; `submit` и `reset` задаются явно.
- Нативная кнопка обеспечивает обычную активацию мышью и клавиатурой. Она не заменяется `div` с самодельной клавиатурной логикой.
- `disabled` использует нативный атрибут `disabled`.
- `loading` задаёт `aria-busy` и блокирует действие. Сам по себе он не убирает кнопку из фокуса: используется `aria-disabled` и защита обработчика. Отдельно проверяется предотвращение отправки формы.
- Для действия используется привычный `onClick`. Второй равнозначный `onPress` без необходимости не вводится.
- Доступное имя получается из содержимого или явно переданного `aria-label` / `aria-labelledby`. Библиотека не придумывает подпись за пользователя.
- Переключатель с `aria-pressed` является отдельным поведением ToggleButton; его состояние не добавляется каждой обычной кнопке.
- Автоматическое управление произвольными Promise не встраивается в Button. Состоянием операции управляет вызывающий код или отдельный хук.
- `useButton` рассчитан на нативный `<button>`. Ссылку реализует отдельная ветка `ButtonAdapter` с семантикой `<a>`; произвольный `as` не поддерживается.

## 11. Проверки и сопровождение

Проверки распределяются по ответственности:

- Ядро: существенные правила вычисления состояния.
- React: действия, недоступные состояния, передача свойств и ref.
- Браузер: клавиатурная активация, фокус, работа внутри формы.
- Тема: визуальные состояния и пример с пользовательской дизайн-системой.
- Каталог: соответствие реальным экспортам и выполнение примеров.

Рядом с компонентом хранятся проверки его контракта. Один и тот же сценарий не дублируется без причины во всех слоях.

Изменение публичного свойства, семантики события или документированного слота рассматривается как изменение API. Внутренние перестановки файлов не должны влиять на пользователей.

Обновления общих пакетов распространяют исправления библиотечной логики. Собственная разметка и поведение, написанные в проекте пользователя, остаются ответственностью проекта; библиотека не обещает автоматически исправлять их.

## 12. Правила роста

1. Новый компонент проходит через необходимые уровни, а не ждёт завершения целого слоя.
2. Нижний уровень не знает об оформлении и агенте.
3. Хук и готовый компонент используют одну реализацию поведения.
4. Локальное расширение не требует форка всей библиотеки.
5. Новый фреймворк добавляется отдельным адаптером к общим контрактам.
6. Новый компонент не обязан становиться отдельным npm-пакетом.
7. Общие абстракции появляются после подтверждённого повторения.
8. Каталог и документация развиваются вместе с публичным API.

Эта архитектура оставляет три уровня доступными пользователю, отделяет зависимости фреймворка от общего ядра и позволяет развивать компоненты, темы и AI-интеграцию параллельно.
