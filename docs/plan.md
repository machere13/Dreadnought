# План реализации библиотеки

Период: 24 сентября 2026 — 15 марта 2027. Основа: [архитектура проекта](architecture.md). Состояние: реализация начата с Button.

## Результат к 15 марта

Работающая React-библиотека с публичными точками входа для логики, компонентов без оформления и готовых компонентов. Есть стандартная и пользовательская тема, каталог библиотеки для AI-агента, сценарий применения дизайна из Figma, документация и измерение времени и LLM-токенов на типовых задачах.

Код компонентов работает без AI-инструментов. Первым сквозным компонентом становится Button. Список остальных компонентов выбирается после его реализации и проверки архитектуры. Button размещён по [правилам проекта](conventions.md): React — в папке второго слоя, оформленный компонент — в третьем слое, тесты — в зеркальных `tests/`.

## Параллельные направления

| Направление | Начало | Продолжается до | Результат |
|---|---|---|---|
| Библиотека: ядро, React-хуки и компоненты | Сентябрь | Февраль | Новые функции и компоненты добавляются по мере появления сценариев |
| Дизайн-система: стандартная и пользовательская темы | Октябрь | Февраль | Готовые компоненты меняют оформление без изменения поведения |
| AI-каталог и доступ агента к нему | Ноябрь | Февраль | Агент выбирает нужный слой по установленной версии библиотеки |
| Figma: получение, сопоставление и повторное применение дизайна | Октябрь: техническая проверка; январь: реализация | Февраль | Пользовательская тема обновляется из Figma с проверкой изменений |
| Проверка продукта и исследование | Октябрь | Март | Работа сценариев, результаты по времени и LLM-токенам |

Работа не ведётся «сначала весь слой 1, потом весь слой 2». Каждый компонент проходит через нужные уровни, а новые хуки добавляются в течение разработки.

## Контрольные точки

### 1. 24 сентября — 20 октября: основание библиотеки и Button

**Создать структуру:** `pnpm-workspace.yaml`, корневые настройки TypeScript, `packages/core`, `packages/adapters/react`, `packages/ui`, `packages/themes` и минимальное приложение в `examples/react`. Зависимости направлены только от верхнего уровня к нижнему; React указан как peer dependency адаптера.

**Реализовать Button:**

1. `packages/core/src/components/Button/`: публичные типы и общие правила `disabled`/`loading`, не зависящие от React.
2. `packages/adapters/react/src/Button/useButton.ts`: свойства и действия нативного `<button>`.
3. `packages/adapters/react/src/Button/ButtonAdapter.tsx`: разметка, передача DOM-свойств и ref.
4. `packages/ui/src/adapters/react/components/Button/`, `packages/ui/src/presentation/Button/` и `packages/themes/src/default/` — готовый React-фасад третьего слоя, общее оформление и стандартные токены.
5. Публичные экспорты для трёх способов использования и страница примеров, импортирующая только эти экспорты.

**Проверить:** обычное действие; `disabled`; `loading`; `type="button"` внутри формы; явно заданный `submit`; работа мышью и клавиатурой; фокус во время загрузки; передача `aria-label`, обработчика, `className` и ref. Проверить, что импорт `logic` и `unstyled` не подключает стандартную тему.

**Готово, когда:** один Button работает в стандартной теме, с ручной пользовательской темой, как компонент без оформления и как собственная разметка на `useButton`. Пример использует те же импорты, что и внешний проект. Зафиксирован документ `docs/components/button.md` с API, состояниями и ограничениями.

### 2. 1–15 октября параллельно: проверить путь из Figma

Взять один конкретный дизайн Button с вариантами и состояниями. Проверить доступность его визуальных данных через выбранный способ интеграции и сопоставить их с токенами и стилями темы. Результат записать в `docs/figma-feasibility.md`: какие данные извлекаются, что требует решения агента, что нельзя вывести из файла надёжно.

**Готово, когда:** вручную воспроизведена тема Button по данным Figma и известен формат входа для будущей автоматизации. Эта проверка не меняет исходники логики Button.

### 3. 21 октября — 15 декабря: развивать компоненты и темы

После Button выбрать следующие компоненты по двум признакам: насколько они часто нужны в интерфейсах и какие новые архитектурные случаи они проверяют. Хотя бы один из них должен иметь управляемое состояние и составную структуру, чтобы подтвердить масштабируемость не только на простой кнопке.

Для каждого компонента повторять цикл: контракт → логика → React-реализация → оформление → пример → проверки → документация. Общие действия, например копирование или скачивание, добавлять там, где для них появляется конкретный пользовательский сценарий; они могут дополнять уже готовые компоненты.

Параллельно развивать стандартные токены, семантические токены и способы локальной замены темы. Не вводить общий движок состояний или универсальный `mergeProps`, пока разные компоненты не покажут одинаковую потребность.

**Готово, когда:** выбранные компоненты работают с одной стандартной и одной пользовательской темой, а добавление нового компонента не требует изменений внутренних файлов существующих компонентов.

### 4. Ноябрь — январь: AI-каталог библиотеки

Для реализованных компонентов хранить явные метаданные рядом с кодом: назначение, доступные слои, пути импорта, состояния, части для оформления, ограничения и допустимые примеры. Генератор получает экспорты и типы из исходников и объединяет их с этими метаданными в версионированный каталог.

Добавить проверку, что каталог ссылается на существующие экспорты, примеры используют актуальный API, а версия каталога соответствует версии пакетов. Сначала предоставить каталог как локальные файлы и Skill. MCP добавить после проверки, что агенту нужен запросный доступ, а не чтение небольшого файла.

Использовать Graphify для анализа связей исходного кода после появления компонентов. Сравнить его извлечённые связи с явными метаданными каталога; не выдавать предположительные связи графа за публичный API.

**Готово, когда:** агент по запросу о Button выбирает корректную точку входа для одного из трёх сценариев и не ссылается на внутренний файл. Обновление публичного экспорта обнаруживает рассинхронизацию каталога при проверке проекта.

### 5. Январь — февраль: применение дизайна из Figma

Реализовать последовательность: получить данные выбранного Figma-компонента → сопоставить варианты и состояния с контрактом темы → предложить изменения пользовательских токенов и CSS → проверить результат в примере проекта.

Сохранять соответствия между элементами Figma и элементами темы, чтобы повторная синхронизация не начиналась с нуля. Если файл темы менялся локально, показывать конфликт. Если дизайн требует другой DOM-структуры, агент выбирает слой 2 или 1 и сообщает об этом явно.

**Готово, когда:** тема Button обновляется после изменения дизайна без изменения `useButton` и `ButtonAdapter`; ручная правка пользовательской темы остаётся доступной.

### 6. 15 февраля — 8 марта: интеграционная проверка и измерения

Проверить три маршрута на одинаковых заданиях: готовый компонент, готовый компонент с собственной темой, собственная реализация на логике первого слоя. Сравнить с разработкой без данной библиотеки при одинаковом агенте и формулировке задачи.

Для каждого задания сохранять время до работающего результата, входные и выходные LLM-токены, число исправлений, корректность поведения и доступности. Заранее фиксировать задания и критерии успешности, чтобы не подбирать их под итоговые цифры.

**Готово, когда:** есть воспроизводимые примеры, таблица результатов и описаны случаи, в которых библиотека не дала выигрыша.

### 7. 1–15 марта: выпуск дипломной версии

Зафиксировать совместимые версии пакетов, каталога и примеров. Проверить установку и импорт из чистого внешнего проекта. Подготовить документацию по трём сценариям, демонстрацию Button, пользовательской темы и обновления из Figma. Закрыть ошибки, мешающие этим сценариям.

**Готово, когда:** проект можно установить, запустить и повторить демонстрацию по документации; результаты исследования включены в материалы диплома.

## Ближайшая техническая последовательность

1. Создать workspace и минимальные пакеты с публичными экспортами.
2. Добавить один значимый тест для состояния Button и реализовать общее правило в `core`.
3. Добавить проверку поведения `useButton` и `ButtonAdapter`, включая форму и клавиатуру.
4. Добавить `Button`, стандартный CSS и ручную вторую тему.
5. Проверить все три уровня использования в `examples/react`.
6. Описать публичный контракт Button и прогнать Graphify по появившемуся коду.

После каждого пункта проект должен собираться; несвязанные возможности Button не добавляются заранее. Следующая работа начинается с пункта 1.
