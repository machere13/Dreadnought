# Правила структуры и именования

Эти правила действуют для всей библиотеки. При изменении существующего компонента его файлы приводятся к ним.

1. **Слой 2 — структура и адаптация под фреймворк.** React находится в `packages/adapters/react/`. Здесь задаются разметка, порядок частей и связь логики с фреймворком. Если появится другой веб-фреймворк, его адаптер размещается рядом с `react/`, без изменений структуры первого слоя.
2. **Тесты — отдельно от исходников.** В каждом пакете `tests/` находится на одном уровне с `src/` и повторяет его структуру. Например, `src/Controls/Button/ButtonAdapter.tsx` проверяется в `tests/Controls/Button/ButtonAdapter.test.tsx`. Тестовых файлов внутри `src/` нет.
3. **Компоненты и их папки — PascalCase.** Имена компонентов, соответствующих файлов и папок: `Button`, `ButtonAdapter`, `Button.tsx`, `ButtonAdapter.tsx`, `src/Controls/Button/`, `tests/Controls/Button/`.
4. **Функции и хуки — camelCase.** Имена функций, хуков и соответствующих файлов: `getButtonState`, `useButton`, `getButtonState.ts`, `useButton.ts`.
5. **Имя сущности любого компонента — `[Компонент][Слой]`.** `XCore` обозначает контракт первого слоя, `XAdapter` — неоформленный компонент второго, `X` — готовый оформленный компонент третьего. Например: `ButtonCore` → `ButtonAdapter` → `Button`. `Button` находится в `ui/react` и использует `ButtonAdapter`; общий CSS и токены третьего слоя не зависят от React. Функции и хуки сохраняют camelCase.
6. **Возможность кладётся по её ответственности, а не по компоненту, который использовал её первым.** Критерии для категорий `core` приведены ниже; запланированный состав — в [core-capabilities.md](core-capabilities.md).
7. **Оформление готового компонента — только в CSS Module.** Готовые React-компоненты находятся в `packages/ui/src/adapters/react/components/`, а общие для веб-фреймворков CSS Modules и карты классов — в `packages/ui/src/presentation/`, например `presentation/Controls/Button/Button.module.css`. Папка `ui/src/adapters/` содержит визуальные адаптеры третьего слоя для разных фреймворков; она не заменяет `packages/adapters/` второго слоя. Оформленный фасад третьего слоя применяет общие классы к адаптеру второго. Все настраиваемые визуальные значения берутся из публичных `--dreadnought-*` токенов темы. Глобальны только объявления CSS-переменных и шрифтовые классы `.dreadnought-text-*`; глобальных селекторов компонента и reset в библиотеке нет. `core` и адаптеры второго слоя не импортируют CSS. Готовая точка входа `ui/react` сама подключает стандартные стили и тему.
8. **Токены темы разделяются по области действия и назначению.** `themes/default/tokens/global/` содержит действительно общие значения, `themes/default/tokens/components/<Семейство>/<Компонент>/` — настраиваемые значения конкретного компонента. Внутри этих папок токены разбиваются на файлы по назначению: `colors.tokens.css`, `spacing.tokens.css`, `typography.tokens.css` и т. д.; общего `constants.css` или единого `tokens.css` нет. Суффикс `-x1`, `-x2` используется только для числовой шкалы (`--dreadnought-spacing-x1`, `--dreadnought-border-radius-x1`), но не для категорий вроде `solid`, `pointer` или `none`. Общие значения с определённой ролью называются по этой роли (`--dreadnought-color-action-primary`, `--dreadnought-opacity-disabled`, `--dreadnought-size-control-min-height`), без привязки к конкретному компоненту. Имена опубликованных ступеней шкалы не перенумеровываются при её расширении. Порядок зависимостей: глобальные токены → токены компонента → его стили. Токен компонента ссылается на глобальный только тогда, когда значение действительно общее; иначе его значение задаётся непосредственно в теме компонента. Не создаём глобальный токен ради формального промежуточного звена. Классы типографики компонента не являются токенами и находятся отдельно в `themes/default/components/<Семейство>/<Компонент>/typography.css`.

Первый слой Button представлен типом `ButtonCore` и функцией `getButtonState`, второй — компонентом `ButtonAdapter`, третий — готовым `Button`, CSS и темой. Для нового веб-фреймворка нужны отдельные адаптер второго слоя и тонкий фасад третьего; CSS и токены остаются общими.

Импорты темы организуются по папкам: `tokens/global/index.css` собирает глобальные токены, `tokens/components/<Семейство>/<Компонент>/index.css` — токены компонента, `components/<Семейство>/<Компонент>/index.css` — его токены и шрифтовой класс. Корневой `themes/default/index.css` импортирует только глобальную точку входа и по одной точке входа на компонент. При добавлении токена меняется локальный `index.css`, а не корневой файл темы.

Экспорты TypeScript собираются так же по областям: в `core` папки `actions/`, `behaviors/` и каждый `components/<Семейство>/<Компонент>/` имеют свой `index.ts`, `components/index.ts` собирает компоненты, а корневой `src/index.ts` экспортирует только разделы. В адаптере и UI каждый компонент также имеет `index.ts`, корневой файл экспортирует только компонентные точки входа. Внутри реализации импортируем конкретные файлы напрямую, чтобы не создавать циклические зависимости через публичные реэкспорты. Близкие файлы импортируем относительно с реальным расширением (`.ts` или `.tsx`); для длинных межобластных путей используем внутренний алиас пакета. В `core` это `#behaviors/*`: TypeScript разрешает его в исходник, Node — в собранный `.js`. Компилятор переписывает только относительные пути.

Для импорта общего оформления из визуальных адаптеров используем внутренний алиас `#presentation/*`, заданный в `packages/ui/package.json` через `imports`. Например: `#presentation/Controls/Button/buttonPresentation.ts`. Алиас доступен только внутри пакета `@dreadnought/ui` и не является публичным путём для потребителей. UI-пакет собирает JavaScript через Vite, а TypeScript выпускает только декларации; это позволяет сохранять `.ts` и в алиасе.

## Storybook

Истории Storybook показывают готовые компоненты третьего слоя и их состояния. Настройки `args` должны доходить до компонента; для специфичных пропсов добавляем явные Controls. Нативные DOM-пропсы не перечисляем по одному, а React-элементы (`icon`, `target`) показываем отдельными историями вместо несериализуемых Controls. Отдельные истории `Unstyled` для адаптеров второго слоя не добавляем: использование адаптеров описывается в документации и проверяется тестами.

## Публичные импорты

Публичный импорт — поддерживаемый путь из другого проекта, объявленный в `exports` пакета. На текущем этапе доступны:

- `@dreadnought/core` — общие действия, поведение и контракты компонентов первого слоя.
- `@dreadnought/react/logic` — React-хуки второго слоя; `@dreadnought/react/unstyled` — неоформленные React-адаптеры. Корень `@dreadnought/react` объединяет оба набора для удобства.
- `@dreadnought/ui` — карты классов оформления без зависимости от React; для их использования стили подключают через `@dreadnought/ui/style.css` и нужную тему.
- `@dreadnought/ui/react` — готовые React-компоненты третьего слоя; этот вход сам подключает стили компонентов и стандартную тему.
- `@dreadnought/themes/default.css` — стандартная тема при явном подключении оформления.

Пути вида `@dreadnought/*/src/...` и внутренний `#presentation/*` не являются публичным API. Подмаршруты для отдельных компонентов и действий пока не открываем: нужные сущности доступны через перечисленные входы. Публичный контракт проверен установкой упакованных пакетов в отдельный проект и сборкой его с `@dreadnought/ui/react`.

## Типографика

- Глобальные роли текста: `h1`–`h6` — заголовки по уровню визуальной иерархии; `body-1`–`body-3` — основной текст от крупного к мелкому; `label-1`–`label-2` — названия полей, элементы управления и короткие подписи к ним; `caption-1`–`caption-2` — вспомогательный текст и пояснения. Номер `1` обозначает самый крупный вариант внутри семейства.
- Каждая роль задаёт `font-size`, `font-weight` и `line-height`. Общий шрифт задаётся `--dreadnought-font-family-ui`. В `typography.tokens.css` объявления сгруппированы по CSS-свойству: сначала все `font-size`, затем `font-weight`, `line-height` и `font-family`. Названия `*-x1` в типографике не используются.
- Button по умолчанию ссылается на `label-1`, Input и TextArea — на `body-2`. Сначала выбираем подходящую роль, затем при необходимости переопределяем токен конкретного компонента или экземпляра. Не создаём глобальную роль для каждого компонента (например, `control`).
- Роль текста описывает внешний вид, а не HTML-тег: `h2` как стиль не подменяет семантику заголовка второго уровня. Токены не создают разметку или компоненты автоматически. Новую роль добавляем при реальной потребности, а не заранее.

## Цвета

- Числовые значения цвета в теме, CSS Modules и примерах записываются современным синтаксисом `rgb(R G B / A%)`, например `rgb(255 255 255 / 100%)` или `rgb(255 255 255 / 50%)`. Каналы `R`, `G`, `B` — целые числа от 0 до 255, прозрачность указывается явно в процентах. HEX и старый синтаксис `rgba(...)` не используем.
- Общие цвета называются по смысловой роли: действие (`color-action-primary`), текст (`color-text-primary`, `color-text-on-action-primary`), поверхность (`color-surface-default`), граница (`color-border-default`), статус (`color-status-error`) и фокус (`color-focus-ring`). Они объявляются в `tokens/global/colors.tokens.css`; цвет конкретного компонента (`button-primary-bg`, `input-border-invalid`) ссылается на общую роль. Одного глобального `color-primary` или `color-secondary` недостаточно: без указания назначения эти имена неоднозначны.
- Стандартная тема — тёмная. `color-surface-canvas` задаёт фон страницы, `color-surface-default` и `color-surface-subtle` — поверхности компонентов; цвет действия не используем как фон страницы. Для выбранных элементов есть отдельный `color-surface-selected`. Текст, границы, фокус и статусы должны сохранять различимость на соответствующей поверхности. Белый фон в Storybook — проверочный фон, а не автоматическое переключение библиотеки на светлую тему.
- Значение, относящееся только к одному компоненту, остаётся в его токенах. Цвета вариантов действия (`color-action-primary`, `color-action-secondary` и их состояния) — общие роли; `button-primary-bg` и `button-secondary-bg` ссылаются на них. Для специальных CSS-значений допустимы `transparent`, `currentColor`, `inherit` и ссылки `var(...)`: это не новые цвета палитры и не повод создавать фиктивный глобальный токен.
- Числовые значения размера, отступа, длительности и угла объявляются в глобальных токенах; токены компонентов только ссылаются на них. Например, `button-icon-size` → `size-inline-graphic`, `button-spinner-radius` → `border-radius-circle`, `button-spinner-duration` → `motion-duration-standard`. Для новых компонентов повторно используем подходящую общую роль, а не копируем числовой литерал.

## Настройка оформления и составных компонентов

Для округлых контролов стандартной темы используется общий `--dreadnought-border-radius-pill`: Button, Badge и Tabs берут его через собственные компонентные токены. `Mark` — декоративный маркер формы `circle`/`square` с необязательным локальным цветом; `Icon` принимает стабильное имя из публичного `IconName`. Соответствие имён SVG хранится только в React-фасаде третьего слоя, поэтому набор иконок можно заменить без изменения пользовательских имён и без зависимости второго слоя от поставщика SVG.

- Токены задают повторяемые значения темы. Токены конкретного компонента можно менять в области проекта, не затрагивая общие токены дизайн-системы. Для одного экземпляра токены задаются через его `className`.
- `className` на простом компоненте относится к его корневому элементу. Повторяемые значения дизайн-системы меняются через токены; отдельное свойство, не вынесенное в токены, можно переопределить пользовательским классом. Не создаём токен для каждого CSS-свойства и не требуем `!important`.
- Обычные стили компонентов и шрифтовые классы библиотеки находятся в `@layer dreadnought`, а пользовательский CSS без слоя имеет над ними приоритет. Например, пользовательский `display: block` перекрывает библиотечный `display: inline-flex`; зачёркнутое правило в DevTools здесь нормально. Порядок подключения файлов не меняет этот результат. Значения токенов `:root` остаются вне слоя; для повторяемой настройки темы используем токены, для отдельного исключения — пользовательский класс без `!important`.
- У составного компонента корневого `className` недостаточно для настройки отдельных частей. Для значимых частей, например строки, заголовка или ячейки таблицы, предоставляем публичные точки настройки: составные подкомпоненты либо `slotProps`/`className` соответствующей части. Выбор формы API зависит от компонента.
- Не раскрываем каждый внутренний контейнер и не предлагаем пользователю обращаться к классам CSS Module или DOM-структуре как к публичному API. Если требуется изменить саму разметку или поведение, используем второй слой вместо переопределения оформления третьего.

## Семейства компонентов

Каждый компонент имеет одно основное семейство по назначению; одна и та же группировка повторяется в `core`, адаптерах второго слоя, `ui` (визуальных адаптерах и `presentation`), токенах и стилях темы, а также в зеркальных `tests/`. Например, Button находится в `Controls/Button`, Input и TextArea — в `Fields/Input` и `Fields/TextArea`. Общие `core/actions` и `core/behaviors` остаются вне дерева компонентов. Папки семейства создаются только при появлении компонента, без пустых каталогов. Публичные импорты не зависят от внутреннего расположения файлов.

Начальный словарь семейств: `Controls`, `Fields`, `Forms`, `Navigation`, `Layout`, `Surfaces`, `DataDisplay`, `Feedback`, `Overlays`, `Content`, `Editors`, `Visualization`. Это навигация по исходникам, а не ограничение функциональности: если компонент подходит нескольким семействам, выбираем одно место хранения, а дополнительные категории указываем в документации и машиночитаемом AI-каталоге без дублирования реализации.

## Страницы документации компонентов

- Все страницы компонентов на сайте используют один шаблон: заголовок и краткое назначение → живой пример и код готового компонента → примеры адаптера и логики → таблица основных свойств и примечания. Пустые разделы не создаём ради симметрии: если у компонента нет соответствующего слоя, явно объясняем ограничение.
- Текст, API-строки и примеры относятся к конкретному компоненту; общий шаблон отвечает только за разметку и порядок разделов. При росте числа страниц данные компонентов выносятся в отдельные файлы, не копируя шаблон.
- Живой пример использует настоящий компонент библиотеки и показывает характерное взаимодействие, а не статичную заглушку. Примеры кода используют публичные импорты каждого слоя и должны соответствовать действующему API.
- Для новой страницы добавляем отдельный маршрут, пункт навигации, проверку доступных заголовков/API и тест ключевого взаимодействия. Проверяем широкую и узкую ширину; длинный код прокручивается внутри своего блока, а не расширяет страницу.

## Открытые вопросы

### Настройка глубоко вложенных частей компонента

Определить публичный способ менять оформление отдельной глубоко вложенной части сложного компонента (например, ячейки таблицы), не обращаясь к случайной DOM-структуре или классам CSS Module. Проверить, когда достаточно наследуемых токенов и слотов, а когда нужны составные подкомпоненты либо `slotProps`/`className` для конкретной части.

## Как делить первый слой

| Категория | Класть сюда, если… | Не класть сюда |
|---|---|---|
| `actions/` | Функция выполняет самостоятельное действие или обращается к браузерному API и может вызываться из разных компонентов: `copy`, `download`, `pickFiles`. | Состояние конкретной кнопки, разметку, React-хук. |
| `behaviors/` | Это переиспользуемое правило вычисления состояния или следующего шага без DOM и внешних эффектов: например, поиск следующего доступного элемента. | Вызовы Clipboard API, управление фокусом DOM-элемента. |
| `patterns/` | Нужен цельный контракт взаимодействия и доступности: семантика, клавиатура, фокус и связанные правила вместе. | Отдельные ARIA-атрибуты без полного поведения. |
| `domains/` | Логика относится к специализированной области, а не к универсальному UI: модель Markdown-документа, геометрия графика. | Общие действия и правила навигации. |
| `components/` | Контракт относится к конкретному известному компоненту и связывает нужные части `core`: `Button`, `Toolbar`. | Общую функцию только потому, что её первым вызвал этот компонент. |

Если код создаёт DOM-разметку или связывает правила с React-событиями и refs, это `adapters/react`, а не `core`. Если задаёт внешний вид, это `ui` или `themes`. Не выделяем общую абстракцию заранее: сначала нужен конкретный сценарий и понятный публичный контракт; повторение в разных компонентах — основание для выноса общего поведения.
