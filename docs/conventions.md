# Правила структуры и именования

Эти правила действуют для всей библиотеки. При изменении существующего компонента его файлы приводятся к ним.

1. **Слой 2 — структура и адаптация под фреймворк.** React находится в `packages/adapters/react/`. Здесь задаются разметка, порядок частей и связь логики с фреймворком. Если появится другой веб-фреймворк, его адаптер размещается рядом с `react/`, без изменений структуры первого слоя.
2. **Тесты — отдельно от исходников.** В каждом пакете `tests/` находится на одном уровне с `src/` и повторяет его структуру. Например, `src/Button/ButtonAdapter.tsx` проверяется в `tests/Button/ButtonAdapter.test.tsx`. Тестовых файлов внутри `src/` нет.
3. **Компоненты и их папки — PascalCase.** Имена компонентов, соответствующих файлов и папок: `Button`, `ButtonAdapter`, `Button.tsx`, `ButtonAdapter.tsx`, `src/Button/`, `tests/Button/`.
4. **Функции и хуки — camelCase.** Имена функций, хуков и соответствующих файлов: `getButtonState`, `useButton`, `getButtonState.ts`, `useButton.ts`.
5. **Имя сущности любого компонента — `[Компонент][Слой]`.** Правило применяется ко всем компонентам библиотеки: `XCore` в первом слое, `XAdapter` во втором, `X` без суффикса в третьем. Например: `ButtonCore` → `ButtonAdapter` → `Button`, `ToolbarCore` → `ToolbarAdapter` → `Toolbar`. Суффикс обозначает ответственность, а не фреймворк: `ButtonCore` не содержит JSX, `ButtonAdapter` создаёт разметку и связывает её с React. Функции и хуки не переименовываются: `getButtonState` и `useButton` остаются в camelCase.
6. **Возможность кладётся по её ответственности, а не по компоненту, который использовал её первым.** Критерии для категорий `core` приведены ниже; запланированный состав — в [core-capabilities.md](core-capabilities.md).
7. **Оформление готового компонента — только в CSS Module.** Файл `src/Button/Button.module.css` содержит локальные селекторы компонента. Все настраиваемые визуальные значения берутся из публичных `--dreadnought-*` токенов темы. Глобальны только объявления CSS-переменных и шрифтовые классы `.dreadnought-text-*`; глобальных селекторов компонента и reset в библиотеке нет. Слои `core` и `adapters` не импортируют CSS.
8. **Токены темы разделяются по области действия и назначению.** `themes/default/tokens/global/` содержит действительно общие значения, `themes/default/tokens/components/<Компонент>/` — настраиваемые значения конкретного компонента. Внутри этих папок токены разбиваются на файлы по назначению: `colors.tokens.css`, `spacing.tokens.css`, `typography.tokens.css` и т. д.; общего `constants.css` или единого `tokens.css` нет. Суффикс `-x1`, `-x2` используется только для числовой шкалы (`--dreadnought-spacing-x1`, `--dreadnought-border-radius-x1`), но не для категорий вроде `solid`, `pointer` или `none`. Общие значения с определённой ролью называются по этой роли (`--dreadnought-color-action-primary`, `--dreadnought-opacity-disabled`, `--dreadnought-size-control-min-height`), без привязки к конкретному компоненту. Имена опубликованных ступеней шкалы не перенумеровываются при её расширении. Порядок зависимостей: глобальные токены → токены компонента → его стили. Токен компонента ссылается на глобальный только тогда, когда значение действительно общее; иначе его значение задаётся непосредственно в теме компонента. Не создаём глобальный токен ради формального промежуточного звена. Классы типографики компонента не являются токенами и находятся отдельно в `themes/default/components/<Компонент>/typography.css`.

Первый слой Button представлен типом `ButtonCore` и функцией `getButtonState`, второй — компонентом `ButtonAdapter`, третий — готовым `Button`. При добавлении новых компонентов сохраняется та же структура.

## Типографика

- Глобальные роли текста: `h1`–`h6` — заголовки по уровню визуальной иерархии; `body-1`–`body-3` — основной текст от крупного к мелкому; `label-1`–`label-2` — названия полей, элементы управления и короткие подписи к ним; `caption-1`–`caption-2` — вспомогательный текст и пояснения. Номер `1` обозначает самый крупный вариант внутри семейства.
- Каждая роль задаёт `font-size`, `font-weight` и `line-height`. Общий шрифт задаётся `--dreadnought-font-family-ui`. В `typography.tokens.css` объявления сгруппированы по CSS-свойству: сначала все `font-size`, затем `font-weight`, `line-height` и `font-family`. Названия `*-x1` в типографике не используются.
- Button по умолчанию ссылается на `label-1`, Input и TextArea — на `body-2`. Сначала выбираем подходящую роль, затем при необходимости переопределяем токен конкретного компонента или экземпляра. Не создаём глобальную роль для каждого компонента (например, `control`).
- Роль текста описывает внешний вид, а не HTML-тег: `h2` как стиль не подменяет семантику заголовка второго уровня. Токены не создают разметку или компоненты автоматически. Новую роль добавляем при реальной потребности, а не заранее.

## Цвета

- Числовые значения цвета в теме, CSS Modules и примерах записываются современным синтаксисом `rgb(R G B / A%)`, например `rgb(255 255 255 / 100%)` или `rgb(255 255 255 / 50%)`. Каналы `R`, `G`, `B` — целые числа от 0 до 255, прозрачность указывается явно в процентах. HEX и старый синтаксис `rgba(...)` не используем.
- Общие цвета называются по смысловой роли: действие (`color-action-primary`), текст (`color-text-primary`, `color-text-on-action-primary`), поверхность (`color-surface-default`), граница (`color-border-default`), статус (`color-status-error`) и фокус (`color-focus-ring`). Они объявляются в `tokens/global/colors.tokens.css`; цвет конкретного компонента (`button-primary-bg`, `input-border-invalid`) ссылается на общую роль. Одного глобального `color-primary` или `color-secondary` недостаточно: без указания назначения эти имена неоднозначны.
- Значение, относящееся только к одному компоненту, остаётся в его токенах. Цвета вариантов действия (`color-action-primary`, `color-action-secondary` и их состояния) — общие роли; `button-primary-bg` и `button-secondary-bg` ссылаются на них. Для специальных CSS-значений допустимы `transparent`, `currentColor`, `inherit` и ссылки `var(...)`: это не новые цвета палитры и не повод создавать фиктивный глобальный токен.
- Числовые значения размера, отступа, длительности и угла объявляются в глобальных токенах; токены компонентов только ссылаются на них. Например, `button-icon-size` → `size-inline-graphic`, `button-spinner-radius` → `border-radius-circle`, `button-spinner-duration` → `motion-duration-standard`. Для новых компонентов повторно используем подходящую общую роль, а не копируем числовой литерал.

## Настройка оформления и составных компонентов

- Токены задают повторяемые значения темы. Токены конкретного компонента можно менять в области проекта, не затрагивая общие токены дизайн-системы. Для одного экземпляра токены задаются через его `className`.
- `className` на простом компоненте относится к его корневому элементу. Для изменения произвольных CSS-свойств, не вынесенных в токены, пользовательский класс должен иметь предсказуемый приоритет над стилями библиотеки. Целевой механизм — CSS cascade layers; до его реализации такая гарантия не считается частью текущего API.
- У составного компонента корневого `className` недостаточно для настройки отдельных частей. Для значимых частей, например строки, заголовка или ячейки таблицы, предоставляем публичные точки настройки: составные подкомпоненты либо `slotProps`/`className` соответствующей части. Выбор формы API зависит от компонента.
- Не раскрываем каждый внутренний контейнер и не предлагаем пользователю обращаться к классам CSS Module или DOM-структуре как к публичному API. Если требуется изменить саму разметку или поведение, используем второй слой вместо переопределения оформления третьего.

## Открытый вопрос: организация множества компонентов

Когда компонентов станет много, плоские каталоги станут трудными для навигации. Это касается `core/src/components/`, адаптеров, готовых компонентов `ui` и компонентных токенов `themes`: для них нужен согласованный принцип группировки и навигации. Пока не выбираем иерархию внутри каталогов компонентов (например, по назначению или по семействам) и не переносим существующие файлы. Перед масштабированием решим, как группировать компоненты во всех слоях, где проводить границу между общей и компонентной частью и как зеркалировать структуру в `tests/`. Публичный API не должен зависеть от расположения внутренних папок.

## Как делить первый слой

| Категория | Класть сюда, если… | Не класть сюда |
|---|---|---|
| `actions/` | Функция выполняет самостоятельное действие или обращается к браузерному API и может вызываться из разных компонентов: `copy`, `download`, `pickFiles`. | Состояние конкретной кнопки, разметку, React-хук. |
| `behaviors/` | Это переиспользуемое правило вычисления состояния или следующего шага без DOM и внешних эффектов: например, поиск следующего доступного элемента. | Вызовы Clipboard API, управление фокусом DOM-элемента. |
| `patterns/` | Нужен цельный контракт взаимодействия и доступности: семантика, клавиатура, фокус и связанные правила вместе. | Отдельные ARIA-атрибуты без полного поведения. |
| `domains/` | Логика относится к специализированной области, а не к универсальному UI: модель Markdown-документа, геометрия графика. | Общие действия и правила навигации. |
| `components/` | Контракт относится к конкретному известному компоненту и связывает нужные части `core`: `Button`, `Toolbar`. | Общую функцию только потому, что её первым вызвал этот компонент. |

Если код создаёт DOM-разметку или связывает правила с React-событиями и refs, это `adapters/react`, а не `core`. Если задаёт внешний вид, это `ui` или `themes`. Не выделяем общую абстракцию заранее: сначала нужен конкретный сценарий и понятный публичный контракт; повторение в разных компонентах — основание для выноса общего поведения.
