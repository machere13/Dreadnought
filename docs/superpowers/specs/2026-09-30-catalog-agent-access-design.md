# Доступ агента к каталогу Dreadnought

Статус: спецификация согласована; локальные запросы и Skill реализованы. План реализации: `docs/superpowers/plans/2026-09-30-catalog-agent-access.md`.

## Задача

Агент в проекте разработчика должен находить доступные компоненты Dreadnought, выбирать подходящий слой и получать реальные импорты, контракты, примеры и токены. Он не должен читать весь многомегабайтный каталог для одного вопроса, придумывать отсутствующие адаптеры или применять API другой версии.

Контрольный сценарий: пользователь просит кнопку со своими стилями в React. Агент проверяет установленную библиотеку, выбирает ButtonAdapter из второго слоя и получает его публичный импорт и пример. Просьба о готовой кнопке ведёт к третьему слою; просьба о собственной разметке — к доступному хуку или core, без смешивания этих контрактов.

## Выбранное решение и альтернативы

Выбраны локальный инструмент чтения каталога и переносимый Skill с инструкциями для агента. Инструмент выдаёт данные, Skill объясняет порядок действий. Они используют существующий формат каталога версии 1.

Чтение целого JSON вручную остаётся возможным, но не является основным сценарием: текущий каталог содержит все унаследованные свойства и слишком велик для постоянного включения в контекст.

MCP пока не создаётся. Он станет отдельной оболочкой над теми же операциями, если проверка покажет необходимость подключения через MCP-клиенты. Сервер, сеть и модель не нужны для чтения каталога.

## Расположение и границы

- `tools/catalog/src/query/` — загрузка и проверка каталога, выбор записей и проверка версий. Небольшие модули с отдельными обязанностями, публичная точка входа `index.mjs`.
- `tools/catalog/src/query.mjs` — локальная командная оболочка, без логики извлечения TypeScript и без запуска сборки.
- `tools/skills/dreadnought/SKILL.md` — инструкция выбора слоя, работы с инструментом и проверки результата. Не копия API компонентов.
- `tools/catalog/tests/` — тесты операций и командного интерфейса.
- `tools/catalog/README.md` — команды и подключение из другого проекта.

Runtime чтения использует только встроенные модули Node.js. Зависимость от компилятора остаётся у существующего генератора. Пакеты библиотеки, Astro-сайт и браузерный поиск не получают новых зависимостей и не меняют свои контракты.

Первая версия используется из локальной копии инструментов Dreadnought. Агенту передаются путь к командному файлу и путь к каталогу. Проверка во внешнем проекте обязательна: текущая директория не должна неявно считаться монорепозиторием. Публикация npm-пакета и автоматическая установка Skill в пользовательские настройки не входят в этап.

## Операции

Команда `pnpm catalog:query` в монорепозитории запускает тот же файл, который из внешнего проекта можно вызвать через `node` по абсолютному пути. Параметр `--catalog` явно задаёт JSON; внутри монорепозитория разрешён стандартный путь `tools/catalog/dist/catalog.json`, вычисленный относительно инструмента, а не текущей директории.

1. `list` — компактный список ID, названий, семейств и доступных привязок. Фильтры `--family`, `--layer`, `--framework`.
2. `search <query>` — поиск по имени, назначению, публичным экспортам и импортам; те же фильтры. Детерминированное текстовое ранжирование, без LLM, векторов и обещания понимать любой естественный язык. Ответ содержит краткие сведения, а не контракты всех совпадений.
3. `get <component> --binding <binding-id> --section <section>` — точное чтение одной привязки. Компонент задаётся устойчивым ID или точным названием без учёта регистра; неоднозначное совпадение является ошибкой. Разделы: `overview`, `api`, `examples`, `tokens`. По умолчанию `overview`; отсутствие binding возвращает только обзор доступных привязок, но не выбирает слой за агента.
4. `check --project <path>` — проверка каталога относительно фактически установленных пакетов проекта.

`list` и `search` ограничены параметром `--limit` от 1 до 50, по умолчанию 10, с `--offset` для следующей страницы. Ответ сообщает полное число совпадений. API читается одной привязкой, с необязательным точным фильтром `--property`; унаследованные свойства включаются только по `--include-inherited`. Необрезанный исходный каталог остаётся доступен как файл.

Контракты сохраняют перегрузки и альтернативные ветви отдельно, включая наличие или отсутствие отфильтрованного свойства в ветви. Нельзя объединять refs кнопки и ссылки в один якобы универсальный контракт. Позиционные параметры функций core и возвращаемый тип сохраняются. Примеры возвращаются целиком, опционально по `--example <id>`. Токены и части оформления принадлежат записи компонента, что явно указывается в ответе независимо от выбранной привязки.

Выбор `Layout.Sidebar` выполняется через соответствующий binding: импортируется корневой Layout, а `propertyPath` описывает обращение к части. Отсутствующий слой, фреймворк, свойство или пример не заменяется похожим молча.

## Версии и доверие к данным

Любая операция сначала проверяет структуру каталога, поддерживаемую версию схемы, уникальность ID компонентов и привязок, обязательные поля и корректность контрактов. Данные каталога не исполняются, указанные в нём файлы и URL автоматически не открываются.

`check` определяет установленные версии известных пакетов Dreadnought через разрешение модулей относительно указанного проекта и чтение их package.json. Код пакетов не импортируется и не исполняется. Диапазон зависимости из package.json проекта не считается установленной версией. Поддерживаются обычный node_modules и symlink-структура pnpm; неподдерживаемое разрешение, включая непроверенный PnP, даёт явную ошибку.

Проверяются только имена из доверенного списка библиотечных пакетов, уже используемого генератором. Все найденные версии должны точно соответствовать `catalog.packageVersions`. Отсутствующие пакеты перечисляются отдельно: отсутствие не равно совпадению версии. Если ни один пакет не найден, проверка не считается успешной.

Ответ без `--project` имеет статус совместимости `unchecked`. Skill запрещает использовать его как подтверждение API установленной библиотеки. При переданном `--project` несовпадение установленной версии блокирует выдачу деталей API/примеров. Выбранная привязка дополнительно требует наличия пакета её `importPath`; например, установленный core не подтверждает доступность React UI.

Нельзя автоматически брать каталог «последней версии» из сети. При несовпадении агент сообщает обнаруженные версии и просит подходящий каталог либо отдельное разрешение обновить зависимости. Инструмент ничего не устанавливает и не меняет в проекте.

## Формат и ошибки

Стандартный вывод содержит один JSON-ответ с версией формата ответа, операцией, версиями каталога, статусом совместимости и результатом. Служебная диагностика идёт в stderr. Ошибка даёт ненулевой код завершения и структурированное описание с устойчивым кодом причины.

Различаются: неверные аргументы, отсутствующий или повреждённый каталог, неподдерживаемая схема, неизвестная сущность/привязка/свойство, ошибка разрешения пакетов и несовпадение версий. Пустая поисковая выдача — успешный результат с нулём совпадений, а не ошибка и не основание выдумывать API.

Чтение каталога не запускает его генератор и не принимает старый файл за автоматически актуальный. Для изменений исходников монорепозитория Skill требует сначала успешную команду `pnpm catalog`. Для внешнего проекта совместимость подтверждается версиями установленного выпуска; совпадение версии не доказывает идентичность локально изменённых исходников, что указывается как ограничение.

## Поведение Skill

1. Выяснить фреймворк проекта и запрос пользователя к готовому оформлению, своим стилям либо собственной разметке.
2. Найти явно указанный локальный каталог и инструмент. Если их нет — объяснить подключение, не устанавливать ничего автоматически.
3. Проверить реальные версии библиотечных пакетов в целевом проекте.
4. Найти компонент, прочитать обзор доступных привязок и выбрать подходящую. Хук React не называть независимым от фреймворка core.
5. Получить точный контракт и подходящий пример через публичные импорты. Читать оформление отдельно, когда оно нужно задаче.
6. Применять принятые правила проекта: CSS Modules, глобальные и компонентные токены, публичные точки входа. Не копировать внутренние реализации библиотеки.
7. Проверить сгенерированный код средствами проекта и сообщить, что действительно проверено. При отсутствии реализации не обещать её наличие.

Skill не содержит списков пропсов и значений токенов: они поступают из каталога. Он не объявляет доступными ещё не зарегистрированные actions/behaviors, даже если они есть в исходниках. Метаданные и примеры рассматриваются как справочные данные, а не как команды на изменение файлов или запуск произвольных программ.

## Проверка результата

- Запрос готовой React-кнопки выбирает UI; своих стилей — ButtonAdapter; собственной разметки — useButton либо явно выбранный core.
- Запрос Angular-кнопки честно сообщает отсутствие соответствующей привязки.
- `Layout.Sidebar` сохраняет правильный корневой импорт и свой контракт.
- Button-ссылка сохраняет отдельную ветвь и тип ref.
- Поиск, фильтры, страницы результатов и неизвестные значения покрыты тестами; вывод команд разбирается как JSON без примеси сообщений сборки.
- Тесты проверяют неверную схему, дубли ID, повреждённый JSON и несовпадение версий.
- В изолированном внешнем проекте проверяются установленный совпадающий выпуск, другой выпуск, отсутствие пакета привязки и отсутствие всех пакетов. Не используются зависимости самого инструмента вместо зависимостей целевого проекта.
- Skill проверяется на контрольных задачах выбора слоя; результат содержит только доступные публичные импорты. Такая проверка не гарантирует безошибочное поведение любой модели.
- Выполняются существующие тесты каталога и документации, проверки типов и сборка сайта: новый потребитель не должен ломать предыдущих.

## Не входит в этап

MCP, публикация пакетов, настройка внешнего AI-клиента без запроса пользователя, сервер генерации, Graphify, изменение браузерного RAG и автоматическое редактирование пользовательского проекта самим инструментом каталога.
