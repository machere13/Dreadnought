# Общий AI-каталог и RAG-помощник документации

Статус: архитектурное решение согласовано. Каталог и RAG ещё не реализованы; следующий этап — общий каталог и его проверки.

## Цель и границы

Помощник объясняет опубликованные возможности Dreadnought, показывает актуальный импорт или пример и ведёт к конкретному разделу документации. Он использует общий машиночитаемый каталог второго AI-контура и опубликованные руководства. Каталог описывает точный API, руководства объясняют его применение, RAG выбирает нужные сведения для ответа.

Сайт остаётся статическим приложением Astro в `apps/docs` с существующими маршрутами и React-компонентами. Генерация ответа выполняется в браузере посетителя. Постоянно работающий сервер модели, векторная база и платный API не входят в первую версию. Генератор каталога и помощник не добавляют AI-зависимостей в runtime UI-библиотеки.

## Общий источник API

Каталог второго AI-контура используется тремя потребителями:

- Skill и MCP дают агенту в проекте сведения об установленной версии библиотеки.
- Сайт документации строит API-таблицы, блоки импортов и общие примеры из записей каталога.
- Поиск и RAG-помощник используют эти записи вместе с руководствами.

Генератор находится в `tools/catalog`. Он читает публичные экспорты и TypeScript-типы библиотечных пакетов, а также явные метаданные рядом с реализацией: назначение, семантические ограничения, состояния, части для оформления, токены, примеры и ссылки на документацию. Набор входных пакетов и точек входа задан явно. Генератор может читать код для проверки публичного API, но не публикует исходники, внутренние пути, проектные планы или произвольные файлы репозитория.

Экспортируемые имена и типы свойств извлекаются из кода; их не переписывают вручную в ещё один список. Назначение и ограничения задаются явно. Неизвестное значение по умолчанию не выводится из optional-типа: оно задаётся проверяемыми метаданными или остаётся неуказанным. Примеры проходят проверку типов через публичные импорты.

Каталог содержит версию формата, версии библиотечных пакетов и записи с устойчивыми идентификаторами. Запись описывает сущность и семейство, доступные слои и реализации под фреймворки, публичные импорты, свойства, состояния, части, токены, ограничения и примеры. Отсутствующие слои не выдумываются: например, наличие React-реализации не означает наличия Angular-реализации. Публичные actions и behaviors также могут иметь записи, без искусственного превращения их в компоненты.

Ссылка `docsUrl` ведёт на реальный маршрут и раздел документации. Каталог может описывать поддерживаемую сущность, для которой страница ещё не опубликована; такая запись остаётся доступной другим потребителям, но не попадает в корпус помощника сайта до появления проверенной ссылки.

## Руководства и поисковый индекс

Второй источник — явно выбранные поясняющие разделы опубликованных Astro-страниц: начало работы, темы, сборка собственных компонентов и руководства по применению. API-таблицы и примеры, уже полученные из каталога, повторно не извлекаются из HTML.

Для руководств используется явная разметка границ индексируемого содержания в статье. Сборщик читает только разрешённые маршруты из результата Astro-сборки и только отмеченные разделы. Шапка, навигация, подвал, интерактивные элементы примеров, кнопки копирования, скрипты и служебная разметка исключаются. Заголовок, иерархия разделов, пояснения и целые примеры сохраняются. Ссылка ведёт на маршрут с существующим якорем; вводный текст может ссылаться на страницу целиком.

`rag-index.json` — производный результат объединения опубликованных записей каталога и руководств. Его не редактируют вручную. Каждый поисковый фрагмент содержит:

- устойчивый `id`, `sourceKind: catalog | guide` и `sourceId`;
- заголовок, раздел, URL, текст и целые примеры кода;
- версии формата и библиотеки через манифест корпуса.

Идентификаторы источников разделены пространствами имён. Одна запись каталога может дать несколько поисковых фрагментов по свойствам, оформлению или примерам, сохраняя связь с исходной записью. Общий объём контекста ограничивается до передачи модели; слишком большой пример пропускается целиком со ссылкой на источник, а не обрезается посередине.

Существующий поиск сайта и помощник используют один производный индекс. Каталог остаётся структурированным JSON для других потребителей; поисковое представление не заменяет его контракт. Браузер загружает статические файлы напрямую, без обращения к MCP.

## Сборка и согласованность

Порядок сборки:

1. Построить и проверить каталог по текущим публичным контрактам пакетов.
2. Собрать Astro-сайт, используя каталог для API-разделов.
3. Извлечь отмеченные руководства из разрешённых HTML-страниц.
4. Проверить ссылки, версии и происхождение записей; сформировать индекс.
5. Опубликовать сайт, каталог и индекс одним артефактом.

Первый этап не зависит от готового HTML: иначе возникнет цикл «каталог → сайт → каталог». Ссылки на страницы проверяются после сборки Astro. При ошибке проверки весь выпуск считается неготовым.

Проверяются существование экспортов, соответствие типов, проверяемость примеров, уникальность идентификаторов, непустое содержимое, разрешённые маршруты, наличие якорей и соответствие версий. Поля API, отображаемые сайтом, не хранятся параллельно в ручных таблицах. Семантическое противоречие в тексте руководства нельзя гарантированно обнаружить проверкой типов: его проверяют при изменении API и на контрольных вопросах.

Индекс относится к конкретной сборке сайта; загрузчик не использует старый кэш при несовпадении версии или идентификатора сборки. Локальная разработка и production используют одинаковые правила построения корпуса. Должен быть предусмотрен явный способ обновить корпус в dev, без ручного редактирования JSON и без скрытого использования устаревшего индекса.

## Поиск и ответ

Поиск работает без модели и WebGPU. В первой версии достаточно текстового ранжирования с повышенным весом названий компонентов, точных имён свойств, заголовков и импортов. Проверочные вопросы определяют достаточность поиска; векторный индекс добавляется только при доказанной необходимости.

На вопрос «как показать пароль в Input?» поиск возвращает запись Input с актуальными свойствами и импортом, а также руководство с объяснением и примером. API берётся из каталога; модель не восстанавливает его по случайному совпадению в тексте.

Результаты со ссылками показываются до генерации. При отсутствии релевантных сведений модель не вызывается. Совпадение общего слова само по себе не считается достаточным основанием для ответа о неподдерживаемой возможности.

После явного запуска браузер загружает WebLLM в Web Worker. Кандидат первой версии — Qwen3-1.7B; точная поддерживаемая сборка, размер загрузки и работоспособность проверяются при реализации. Модель получает вопрос и только найденные фрагменты с идентификаторами. Сведения из источников считаются данными, а не инструкциями модели.

Приложение строит ссылки только по идентификаторам из текущей выдачи. Неизвестные идентификаторы и ответ без проверяемых источников не показываются как подтверждённый ответ. Наличие верной ссылки не доказывает правильность каждой фразы: качество и неподтверждённые утверждения проверяются отдельно. Ответ не выполняет код и не вставляет произвольный HTML.

## Работа в браузере

Перед первым скачиванием пользователь видит размер модели и условия запуска. Загрузка и генерация имеют прогресс, отмену и понятные ошибки. Смена вопроса и отмена исключают показ запоздалого ответа предыдущего запроса.

При отсутствии WebGPU, нехватке памяти или сбое загрузки продолжают работать документация и поисковые ссылки. Веса не включаются в статический пакет сайта. Возможность браузерного кэширования не означает гарантии вечного хранения. История вопросов остаётся в текущей вкладке; серверного хранения нет.

Статический сайт можно публиковать на ранее выбранном хостинге. Доступность источника весов, условия хостинга и реальную скорость загрузки проверяют перед выпуском.

## Проверка результата

- Изменение публичного пропса обновляет каталог и API-таблицу; устаревший пример обнаруживается проверкой типов.
- Одна запись каталога используется сайтом, поиском и интерфейсом доступа второго AI-контура без ручных копий API.
- У помощника нет записей неопубликованных страниц, внутренних планов или чужой версии библиотеки.
- Каждая выдаваемая ссылка открывает нужный раздел; API не дублируется через извлечение HTML-таблицы.
- Вопросы на русском и английском находят нужные API и руководства; неподдерживаемые запросы не получают уверенный ответ по нерелевантному фрагменту.
- Ошибка модели, отсутствие WebGPU и отмена сохраняют работу поиска; устаревший ответ не появляется.
- Реальная модель и демонстрационные вопросы проверяются в целевом браузере на устройстве для показа.

## Последовательность реализации

Сначала генератор и общий каталог с проверками на Button и Input. Затем перевод остальных опубликованных API-разделов на каталог, индекс руководств и общий поиск. После этого — браузерная модель и проверка качества ответов. MCP подключается к тому же каталогу отдельным этапом второго AI-контура и не блокирует помощника сайта.

План работ: [browser-rag](../plans/2026-09-26-browser-rag.md).

## Вне первой версии

Нет серверного инференса, регистрации, постоянной истории чатов, индексации проектных планов, выполнения кода из ответов и многошагового агентного поиска. Создание отдельного MCP-сервера не входит в реализацию помощника документации.
