# Toolbar: контракт трёх слоёв

Статус: утверждён пользователем 2026-10-05; реализован во всех трёх слоях, опубликованы каталог, документация и Storybook. Независимое ревью завершено; два найденных дефекта исправлены и покрыты регрессионными тестами. Повторный полный прогон прошёл: 458/458 тестов, exit 0; ручная визуальная проверка пока не подтверждена.

## Цель и согласованные решения

Проверить композицию возможностей core на панели инструментов с библиотечными и пользовательскими контролами. Панель не создаёт действия, не меняет выбранные значения и не требует использовать только Button.

Согласованы два режима:

- `navigation="roving"`: одна остановка Tab на доступном участнике; стрелки переключают фокус. Для кнопок и контролов, которым не нужны эти же стрелки.
- `navigation="native"`: обычная последовательность Tab; клавиатура остаётся у каждого вложенного контрола. Для смешанных панелей с Input, Select и другими полями.

Это новый компонент семейства `Controls`. Сохраняем имена ToolbarCore, ToolbarAdapter и Toolbar для соответствующих слоёв. Не вводим меню скрытых элементов, overflow, выбор команд или модель редактора в этом этапе.

## Источник правил доступности

Основа: [W3C APG Toolbar](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/), проверено 2026-10-05. APG описывает одну остановку Tab, стрелочную навигацию и конфликт с контролами, которым нужны те же стрелки.

`roving` реализует этот клавиатурный паттерн. `native` — сознательно другой контракт обычной группы: сохраняет Tab у всех контролов и использует `role="group"`, а не объявляет полноценный ARIA-toolbar без его клавиатурного поведения. В документации различие указывается явно. Оба режима требуют доступного названия через aria-label или aria-labelledby. Название компонента Toolbar описывает панель приложения, а role зависит от предоставляемого взаимодействия.

## Рассмотренные способы композиции

1. **Явный хук участника — выбран.** Корень предоставляет контекст, `useToolbarItem` связывает настоящий фокусируемый элемент с панелью. Не создаёт дополнительную обёртку и подходит собственным контролам.
2. **Поиск всех кнопок и полей в DOM.** Меньше кода у пользователя, но неясное участие вложенных меню, служебных кнопок и составных контролов; потребовалось бы изменять чужой tabindex. Не выбираем.
3. **Компонент Item с render-функцией.** Позволяет явно передавать свойства, но в первом варианте не нужен второй API поверх того же хука. Можно добавить после подтверждённой потребности.

## Слой 1: чистый контракт

Добавить в `core/components/Controls/Toolbar` типы ToolbarCoreOptions, ToolbarCore и функцию getToolbarState.

Вход:

- `items`: readonly-массив NavigationItem со строковыми value и необязательным disabled.
- `activeValue?`: последний активный ключ, не выбранная команда.
- `navigation?`: roving или native; по умолчанию roving.
- `orientation?`: horizontal или vertical; по умолчанию horizontal.

Результат:

- `role`: toolbar для roving, group для native.
- `ariaOrientation`: ориентация только для роли toolbar; для group — undefined.
- `tabStopValue`: в roving текущий ключ, если он есть и доступен, иначе первый доступный. Для пустого/полностью disabled списка и native — undefined.

Непустые уникальные ключи проверяются на границе контракта; неверный ключ участника даёт понятную ошибку, а устаревший activeValue является допустимым входом и выбирает первый доступный пункт.

`getToolbarState` не читает DOM, не хранит React-состояние, не вызывает действия и не переносит фокус. Следующий ключ определяется существующим getNextEnabledValue, направление — getNavigationDirection. Нового универсального движка коллекций или отдельного patterns-файла ради копии этих правил не создаём.

В core-примере пользователь самостоятельно связывает state.tabStopValue с tabindex и следующий ключ с фокусом в своём фреймворке. Публичный импорт — `@dreadnought/core`.

## Слой 2: React

### ToolbarAdapter

Публичный импорт — `@dreadnought/react/unstyled`. Корень — div, children — произвольный ReactNode. Нативные свойства, className, style, ref и обработчики передаются без потери.

Собственные свойства:

- `navigation`: roving/native, по умолчанию roving.
- `orientation`: horizontal/vertical, по умолчанию horizontal.
- `loop`: boolean, по умолчанию true; применяется только в roving.

Не добавляем controlled activeValue и callback изменения фокуса без отдельного сценария. Клик и onAction принадлежат контролу. Кнопки с disabled или loading не активируются самой панелью.

### useToolbarItem

Публичный импорт — `@dreadnought/react/logic`. Хук вызывается в отдельном React-компоненте внутри ToolbarAdapter или готового Toolbar. Вход: value, disabled, необязательные ref, onFocus и onKeyDown. Generic ограничен HTMLElement для точного типа ref и событий.

Результат `{ itemProps }`: ref регистрации, tabindex и связанные обработчики фокуса/клавиатуры. Их передают **на настоящий фокусируемый элемент**, не на визуальную обёртку. Переданный потребителем ref сохраняется; пользовательские обработчики выполняются первыми, preventDefault отменяет внутреннюю реакцию.

`disabled` хука определяет участие в навигации, но не заменяет disabled самого контрола и не блокирует его onClick. Потребитель передаёт согласованное состояние в оба места; loading у кнопки также можно исключить из навигации через disabled хука. Нативно отключённые элементы, включая отключение через fieldset, не являются доступными целями фокуса даже при ошибочно пропущенном disabled хука.

Хук вне корня даёт понятную ошибку. В native он не задаёт tabindex и не перехватывает клавиши. Для native подключать хук не требуется: обычные Button, Input, Select и собственные контролы можно вставлять напрямую.

Своим контролам не требуется менять реализацию Button или зависеть от поставщика иконок. Встроенные Button/Input/Select не получают скрытой зависимости от контекста Toolbar.

Пример предлагаемого использования, до реализации не является действующим API:

```tsx
import { useToolbarItem } from '@dreadnought/react/logic';
import { Button, Toolbar } from '@dreadnought/ui/react';

function SaveTool() {
  const { itemProps } = useToolbarItem<HTMLButtonElement>({ value: 'save' });
  return <Button {...itemProps} size="compact">Сохранить</Button>;
}

// В roving каждая участвующая кнопка подключается так же, со своим ключом.
// Кнопку SaveTool можно заменить собственной кнопкой с теми же itemProps.
```

Для смешанной панели:

```tsx
<Toolbar navigation="native" aria-label="Фильтры">
  <Input aria-label="Поиск" />
  <Select aria-label="Статус" options={options} />
  <Button>Применить</Button>
</Toolbar>
```

### Реестр и клавиатура

Реестр хранит только явно подключённые элементы и сортирует их по порядку DOM, не по порядку mount. Не регистрирует descendants вложенного Toolbar в родительском корне. Ref-cleanup удаляет участника без удаления чужой регистрации; StrictMode и смена ref не создают дубликаты.

В roving доступные участники имеют один tabindex=0; остальные -1. disabled пропускаются. При повторном входе сохраняется последний доступный активный пункт. Если он исчез или стал недоступным, новый вход направляется на первый доступный. Изменения коллекции не переносят фокус из другого места страницы обратно в панель.

Если фокусируемый участник удалён или отключён во время фокуса внутри панели, адаптер восстанавливает фокус на первом доступном участнике. Если доступных нет, корень временно получает программный фокус через tabindex=-1; он не становится дополнительной остановкой Tab. Это восстановление не выполняется при начальном mount или при фокусе вне панели.

Горизонтально работают ArrowLeft/ArrowRight, вертикально — ArrowUp/ArrowDown. Другая пара стрелок не перехватывается. Home/End переходят к крайним доступным участникам. loop=false останавливается на краях. Tab/Shift+Tab выходят из панели без ручного перехвата. Enter/Space и действия мышью остаются нативному контролу.

Модифицированные клавиши, IME, события вложенных панелей и потомков, которые сами обрабатывают клавиатуру, не запускают навигацию корня. Корень не слушает глобальные keyboard-события.

В roving разрешён один фокусируемый элемент на участника, без вложенного самостоятельного поля или второго Tab-stop. Поля, составные Select и другие контролы с конфликтующими клавишами требуют native. Библиотека не обещает автоматически распознать все неизвестные пользовательские компоненты; ограничение документируется рядом с примером. Декоративные Badge, подписи и разделители могут быть обычными children и не участвуют в реестре.

## Слой 3: оформление

`@dreadnought/ui/react` экспортирует Toolbar — тонкий фасад ToolbarAdapter. Хук остаётся в React logic; третьему слою не нужна отдельная реализация фокуса.

Общее оформление — `presentation/Controls/Toolbar`, тема — `themes/default/tokens/components/Controls/Toolbar`, локальные index.css и index.ts по конвенциям. Публичные значения отступов, gap, поверхности, границы и радиуса задаются токенами компонента с переиспользованием существующих глобальных значений. Не добавляем новые числовые шкалы ради Toolbar. Стили находятся в CSS Module и @layer dreadnought, без !important.

По умолчанию панель — нейтральная компактная группа без отдельной тяжёлой карточки. Ориентация меняет направление раскладки. Панель не переоформляет вложенные Button, Input или Select; размеры и варианты контролов задаёт потребитель. Корневой className относится к панели; оформление отдельных контролов меняется их собственными API.

## Каталог, документация и проверки

Toolbar публикуется как Controls/Toolbar с привязками core, react-logic, react-adapter и react-ui. Публичные экспорты, варианты navigation, ориентация и loop проверяются генератором. Не выдаём pure-core привязку хука за независимость от React. Примеры проверяются TypeScript.

Документация и Storybook показывают: roving с тремя командами, native с Input/Select/Button, свою кнопку через хук, disabled, вертикальную ориентацию, отключённый loop. Отдельной Unstyled-истории нет; пример адаптера находится в документации. Объясняем role=group в native и отсутствие автоматического подключения произвольных children к roving.

Критерии готовности:

1. Core выбирает действующий tab-stop, обрабатывает пустые/disabled коллекции, устаревший activeValue и ошибочные ключи без мутации входа.
2. В roving одна остановка Tab; стрелки, Home/End, loop, пропуск disabled и возвращение в панель проверены реальными событиями.
3. В native все контролы сохраняют нативные переходы Tab; ввод, курсор и список Select работают без перехвата панелью.
4. Своя кнопка и библиотечный Button используют один хук; ref и отменённые пользовательские события сохраняются.
5. Порядок DOM, динамическое добавление/удаление/disabled, отсутствие участников, вложенные панели, StrictMode и SSR проверены без глобальных обработчиков или чтения DOM при рендеринге на сервере.
6. Изменение панели не забирает фокус с других элементов страницы; восстановление локального фокуса проверено отдельно.
7. UI не дублирует поведение и не влияет на соседние контролы. Каталог, типы, весь набор тестов и сборки проходят.

## Границы первого этапа

Не добавляем overflow, drag-and-drop, двумерную навигацию, пользовательские горячие клавиши, typeahead по командам, редактор, автоматическое сканирование DOM и отдельный компонент каждого декоративного разделителя. RTL-навигация не обещается в первом контракте; ограничение фиксируется в каталоге и документации. Новые зависимости не требуются.

Самостоятельные core-правила уже доступны другим фреймворкам. Готовые Toolbar и useToolbarItem остаются React-реализацией; наличие этого компонента не означает готового Angular-адаптера.
