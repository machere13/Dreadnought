# Сравнение токенов — повторный прогон с MCP

Дата: 2 октября 2026. Два новых независимых агента на `gpt-6-sol` без истории предыдущего теста получили одинаковое ТЗ на экран «Командная доска». Оба стартовали с одинаковой React 19 / TypeScript 5.9 / Vite 7 базой и уже установленными зависимостями; настройка окружения не входит в токены агентов. Оба использовали `ponytail`. Агент с Dreadnought дополнительно прочитал проектный Skill и получал сведения о компонентах **через настоящий локальный MCP stdio-сервер**, не из исходников.

| Показатель | Dreadnought + MCP | React + CSS |
| --- | ---: | ---: |
| Входные токены, всего | 1 454 199 | 588 518 |
| Из них кешированные | 1 368 704 | 551 936 |
| Входные без кеша | 85 495 | 36 582 |
| Выходные токены | 11 083 | 11 070 |
| Входные без кеша + выходные | **96 578** | **47 652** |
| Все токены, включая кеш | 1 465 282 | 599 588 |
| Собственный App.tsx + style.css, байт | 10 027 | 11 685 |
| JS в production build, gzip | 84,27 КБ | 71,09 КБ |
| CSS в production build, gzip | 8,18 КБ | 1,69 КБ |
| Production build | прошёл | прошёл |

**Результат одного прогона:** с MCP вариант Dreadnought потребовал в **2,03 раза больше** некешированных входных и выходных токенов, хотя собственный код экрана на 14,2% меньше по объёму. Выходных токенов почти одинаково: 11 083 против 11 070. Основная разница — входной контекст (85 495 против 36 582). Вероятная причина — объём возвращаемых сведений каталога; это вывод из счётчиков, а не отдельное измерение стоимости каждого ответа.

MCP использовался фактически: `dreadnought_check` подтвердил совместимость установленных пакетов 0.1.0; агент выполнил 32 успешных запроса `check`, `search`, `get` для обзоров, API, примеров и токенов. Ещё 7 попыток завершились ошибками песочницы или аргументов. По журналу вызовов агент не читал исходники компонентов, документацию или прошлые benchmark-решения вместо каталога. Применены Button, Input, Card, Badge, Tabs и Table.

Перед прогоном попытка регенерировать каталог завершилась ошибкой памяти Node. Использован существующий `catalog.json`; MCP-проверка подтвердила совпадение версий пакетов, но не доказывает свежесть каталога относительно каждого исходного файла.

Обе финальные сборки независимо перепроверены. Обязательные состояния, поиск, фильтры, форма и счётчики присутствуют в коде обоих экранов. Одинаковый браузерный кликовый тест провести не удалось: встроенный браузер не смог подключить локальную вкладку. Поэтому функциональная эквивалентность не подтверждена интерактивно; вывод выше относится к затратам агентов на собранные реализации.

Числа получены из `token_usage_record.thread_token_usage` журналов двух агентов. Кешированный ввод показан отдельно; сумма «вход без кеша + выход» не равна денежной стоимости API. Это один прогон, не статистическая оценка. В отличие от первого прогона, он проверяет предусмотренный путь Skill → MCP → каталог → код; следующий предмет оптимизации — насколько компактно каталог отдаёт агенту **только нужные** свойства, примеры и токены.

## После добавления компактного запроса

Добавлен `dreadnought_context`: агент выбирает нужные компоненты по задаче и получает их публичные импорты, имена свойств и слотов, пример и доступные типы одним ограниченным ответом. Подробности запрашиваются через `get` только при необходимости. Проверка через настоящий локальный MCP для тех же шести компонентов вернула 7 880 байт при лимите 8 192 байта, без обрезки.

Для оценки размера контекста повторили типовую последовательность старого маршрута для шести компонентов: `check`, затем для каждого `search`, `overview`, `api`, `examples`, `tokens`. Получилось 31 ответ общим размером 62 466 байт против одного ответа `context` размером 7 880 байт (на 87,4% меньше UTF-8 байтов). Это **сравнение объёма ответов каталога**, а не новый подсчёт токенов агента: фактическую экономию в полной реализации экрана нужно проверить отдельным повторным прогоном.
