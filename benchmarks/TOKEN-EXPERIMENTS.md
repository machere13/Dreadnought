# Эксперименты без изменения библиотеки

Дата: 3 октября 2026. Цель: меньший расход токенов при создании одинакового экрана с существующими компонентами, без CollectionPage и без добавления готового экрана в библиотеку.

В v11 получен выигрыш и в независимом подтверждающем v12 с обратным порядком запуска повторён. Это ограниченный положительный результат, не доказательство большой устойчивой экономии. Полный поток во втором прогоне уменьшился всего на 0,36%.

Кеширование различается; некешированный вход + выход не является ценой в деньгах, кешированные токены тоже могут тарифицироваться.

## Что изменилось в способе работы

1. Стартовые файлы, Ponytail, короткая инструкция и пакетный MCP-запрос читаются одним вызовом, а не цепочкой разведки проекта/API.
2. Агент получает проверенные примеры применения шести конкретных компонентов и небольшой список допустимых простых свойств. Полный API остаётся доступным точечно. Примеры не содержат предметной логики или решения экрана.
3. Указаны границы готового оформления: CSS приложения описывает расположение, а не повторяет внутренние стили компонентов.
4. Исправлена ошибочная выдача одиночного undefined вместо наследуемого Button.type; добавлено короткое общее правило TypeScript для вынесенных Table columns. Библиотечный код не менялся.

Примеры сами по себе оказались недостаточны (v9): агент дополнительно запрашивал API. Неполные сокращённые типы тоже приводили к лишней работе (v10). Версии v11/v12 — текущий экспериментальный способ; перенос в основной инструмент пока не выполнен.

## Проверки и границы вывода

В v11 и v12: четыре успешные production-сборки, 16 успешных функциональных проверок, просмотр всех четырёх экранов при 1280/360 px и проверка Escape. Исправлений реализаций после внешних проверок не потребовалось. Независимость инструкционная, не OS-изоляция. Пиксельное совпадение и равное визуальное качество не доказаны. Стоимость создания библиотеки, подготовки проектов, анализа и внешней проверки исключена из агентских метрик, а не объявлена бесплатной.

Задание: [TASK.md](token-comparison-v11/TASK.md). Детали и исходные метрики: [v11](token-comparison-v11/RESULTS.md), [v12](token-comparison-v12/RESULTS.md), `metrics.json` в каждой папке. Все неудачные попытки сохранены.

Дальнейшая проверка для заявления об устойчивой экономии: заранее зафиксированная серия разных задач без настройки инструмента между ними; учитывать все результаты, полную стоимость и одинаковые критерии поведения/качества.

## Перенос и качество (следующий этап)

Подход перенесён в основной `context`: формат `usage` по умолчанию, `contract` для ветвей, точечный `get` для недостающего API. Проверенные примеры включены в генератор, скилл обновлён. Экспериментальный bootstrap с чтением стартового проекта не является частью MCP: его нельзя выдавать за универсальный API библиотеки. Точные проценты v11/v12 относятся к прежнему стенду; после переноса они не измерялись заново.

В v12 обнаружен недостаток мобильного вида Tabs: сжатие/перенос подписей и внешняя обёртка для прокрутки. Библиотечные стили списка ограничивают max-width, но не определяют политику переполнения; табы по умолчанию могут сжиматься и переносить текст. Это кандидат на исправление в компоненте, а не повод добавлять CSS-обход в каждое приложение. Аналогичные дефекты остальных компонентов этим экспериментом не подтверждены.

Для следующих сравнений заранее фиксировать: требования к виду при 1280/360 px, функции, клавиатуру/фокус/подписи и читаемость кода. Любой вариант должен пройти все требования; токены до исправления недостатков не считать финальной стоимостью. Дефект библиотеки исправляется отдельно в библиотеке и её версия фиксируется до нового чистого прогона. Стоимость такого исправления учитывается отдельно, не скрывается в CSS приложения. Нельзя убирать детали интерфейса, состояния или проверки ради хорошей цифры.

Безопасные направления следующей оптимизации: исключать повторные запросы уже полученного API; давать точные короткие примеры сложных свойств, чтобы снижать число исправлений; измерить задачи, использующие уже существующие возможности компонентов (например, сортировку и выбор строк Table), с одинаковыми требованиями к обеим реализациям. Готовые экраны в библиотеку для этого не добавляются.
